1. Executive Summary

This review discovers the full attendance-policy architecture of the Timex system, identifies all hard-coded values and structural gaps, and delivers a final implementation specification. The goal: make attendance configurable via the existing Policy/PolicyValue infrastructure, enable Late/Early tracking, and provide a clear path for reports.

Key Discoveries

  1. 7:20 (7.33h) is hard-coded in 11+ locations across attendance.py, admin.py, detailed_monthly_report_v2.py, and analytical_report.py. There is no policy lookup anywhere in the attendance path.
  2. No Schedule/Shift model exists. There is no per-employee or per-department scheduled start/end time. "Shift" in time_calculator.py means morning/evening/night time-of-day bands — not a shift assignment.
  3. No Late/Early logic exists. Zero code computes lateness or early departure. This is entirely new functionality.
  4. Employee.department is a free-text String(100) used as a numeric group code ('1'-'5'). It is NOT the contract type. The real contract type lives in Contract.contract_type_code ('1'-'7').
  5. Latent bug in attendance.py:460: Employee.department if Employee else None compares against an unhydrated SQLAlchemy Column object, not an employee's department value.
  6. policies.html already has a disabled "حضور و غیاب" card (line 68-81), confirming the infrastructure was designed to be extended.
  7. The Policy model's category column comment literally says "leave / attendance / overtime / absence", confirming the 'attendance' category was anticipated.
  8. Phase 1's DEFAULT_REQUIRED_HOURS = 8.0 is NOT supported by any code in the repository. Every location uses 7.33/7:20. This is an open business decision.

Key Observations

  • User → Employee: 1:1 via unique user_id FK. Employee is the stable identity.
  • Employee → Contract: 1:N temporal. get_active_contract(user_id, target_date) resolves the active contract for any date.
  • Employee → EmployeeRegion: 1:N temporal via effective_from/effective_to. This is the precedent for date-scoped attribute resolution.
  • No Schedule/Shift table exists: No table stores planned start/end times for any employee or department.
  • No AttendancePolicy table exists: All attendance configuration is currently hard-coded.

Which Should Be the Policy Scope?

For attendance policy purposes, the key question is: what determines an employee's work hours requirement?

  • Option A: Employee.department ('1'-'5') — Used today by reports and holidays. Only 5 values. But it's a free-text field with no FK constraint, no validation, and is set once at creation.
  • Option B: Contract.contract_type_code ('1'-'7') — The authoritative employment type. Has 7 values. Is date-scoped (an employee can have different contract types over time). Has a resolver: get_active_contract().
  • Option C: A new AttendancePolicy entity — Explicitly assigned per-employee or per-group, decoupled from both department and contract type.
This is a critical architecture decision. See Section 8 for full comparison. See Decision #1.

4. Schedule / Workday Analysis

Current Workday Definition

The system has no formal "workday" concept. The day-off logic is entirely hard-coded:

  • Friday (weekday==4): always a day off
  • Holiday: from Holiday table (national or group-specific)
  • Rest day: DailyStatus code 'R' — treated as a day off in duty calculation
  • Leave: approved LeaveRequest — treated as a day off in duty calculation
  • Mission ('M'): DailyStatus code 'M' — NOT excluded from duty days. A mission day is still a work day.
There is NO per-weekday schedule. No "Saturday is a work day, Sunday is off" beyond the Friday rule. Every non-Friday, non-Holiday day is a potential work day.

No Scheduled Times

Zero tables, zero code defines when an employee is expected to start or end their work day. The word "shift" in core/time_calculator.py refers to time-of-day band selection (morning 06:00-14:00 / evening 14:00-22:00 / night 22:00-06:00) for hour calculation, NOT a shift assignment.

This means: Late and Early Leave cannot be computed without adding scheduled times. See Sections 12-13.

5. Required Work Analysis

How Duty Hours Are Calculated Today

Both the user view (attendance.py:601-674) and manager view (admin.py:1082-1137) use identical logic:

work_days = total_days - fridays - holidays      # non-off days
duty_days = work_days - leave_days - rest_days   # subtract absences
monthly_duty_hours = duty_days × DAILY_DUTY_HOURS  # DAILY_DUTY_HOURS = 7.333
monthly_balance = actual_work_hours - monthly_duty_hours

Where DAILY_DUTY_HOURS = 7 + 20/60 = 7.333... (7 hours and 20 minutes).

6. 7:20 Hard-code Analysis

Why 7:20?

The value 7:20 (7 hours, 20 minutes = 7.333 hours) appears to be the official daily required work hours per Iranian labor law for a standard 44-hour work week (44 / 6 working days ≈ 7.33). However:

  • The repo hard-codes this for ALL employees regardless of contract type
  • Contract types '5' (پزشک), '6' (سایر), '7' (قرارداد با بیمهها) have 0 annual leave in CONTRACT_TYPES, suggesting different rules — but no different work hours
  • No code anywhere resolves "what are this employee's required hours?" — it's always the global constant

Impact of Hard-coding

  • Balance calculation is wrong for any employee whose actual requirement differs from 7:20
  • Reports (V2 and analytical) use 7.33 as a fixed value, with a comment in analytical_report.py: "# بعداً تغییر میکند" ("will change later") — confirming the developer intended this to be configurable
  • Overtime calculations are downstream of this; wrong duty hours → wrong overtime

How Leave Policy is Resolved

The leave policy uses a per-department key pattern: carry_forward_dept_1, annual_leave_dept_2, etc. The _dept_{N} suffix matches Employee.department values. Region override is via a separate region_applies_dept_{N} key.

The existing Policy/PolicyValue infrastructure is fully capable of supporting attendance policy. No new tables or schema changes are required.

EmployeeRegion — Temporal Precedent

EmployeeRegion(user_id, region_code, effective_from, effective_to) is the only date-scoped attribute resolution in the system. Its pattern (nullable effective_to for "current") is the model for any future temporal policy resolution.

8. Policy Scope Options

Question: What determines an employee's attendance policy (required hours, late rules, etc.)?

Option A: Contract Type (contract_type_code)

Approach: Resolve the employee's active contract via get_active_contract(user_id, target_date), then use contract.contract_type_code to look up policy parameters.
Pros: Already date-scoped; authoritative employment type; 7 distinct types.
Cons: Requires joining Contract on every attendance calculation; contract_type codes (1-7) don't match department codes (1-5) in existing leave policy keys; two employees with same contract_type may need different schedules.
Key issue: Leave policy already uses department codes ('1'-'5'), not contract codes ('1'-'7'). This would create two parallel scoping systems.

Option B: Employee Department (department field)

Approach: Use Employee.department (the existing group code '1'-'5') as the policy scope key, matching the leave policy pattern.
Pros: Consistent with existing leave policy keys (_dept_{N}); already used by reports and holidays; no join needed (Employee is already loaded).
Cons: Free-text field with no FK constraint; only 5 values; doesn't capture per-employee overrides; values could be misspelled.
Key issue: This perpetuates the department-as-group conflation. It works, but it's architecturally impure.

Option C: Explicit Policy Assignment (new field or join table)

Approach: Add a policy_group field to Employee (or use a mapping table), explicitly linking each employee to an attendance policy group. The group determines default parameters, with optional per-employee overrides via PolicyValue.
Pros: Decoupled from both department and contract type; supports per-employee overrides; clean separation of concerns; can evolve independently.
Cons: Requires a new field (migration); requires initial data population; adds one more lookup.
Key issue: The existing Employee.department already functions as a policy group in practice. Adding another field may be over-engineering.

Option D: Hybrid — Department as default, per-employee override via PolicyValue

Approach: Use Employee.department as the default policy scope (matching the existing _dept_{N} pattern), BUT allow per-employee overrides by adding PolicyValue entries with a user_id scope instead of region_code.
Pros: Backward-compatible with leave policy pattern; supports exceptions; no new fields; uses existing infrastructure.
Cons: Slightly more complex resolution logic; still relies on the department field being properly set.
This is the recommended approach. It builds on proven patterns and requires minimal change.
Decision #1: Policy Scope
Question: What determines an employee's attendance policy (required hours, scheduled times, late/early rules)?
Why it matters: This is the foundational design decision. Every downstream component (policy resolution, report calculation, UI) depends on this.
Options: (A) Contract type, (B) Department, (C) Explicit assignment, (D) Hybrid dept+override.
Recommended: Option D — Hybrid. Use Employee.department as the default scope (consistent with leave policy), with per-employee PolicyValue overrides.
Needs user confirmation: YES

Resolution Order

resolve_attendance_policy(user_id, target_date):
  1. Get employee's department code
  2. Look up PolicyValue(category='attendance', key=param, suffix='_dept_{code}')
  3. If per-employee override exists (new key pattern: 'param_user_{user_id}'), use it
  4. If no policy found → use system default (see Section 10)

Why NOT per-Contract-Type?

The leave policy already established the _dept_{N} pattern. Using a different scoping mechanism for attendance would create confusion. The department field, while imperfect, is the proven convention. Per-employee overrides handle any exceptions.

10. Default Policy Decision

When no PolicyValue entry exists for an employee, what should the system do?

Options

Option A: Use 8.0 hours (Phase 1 suggestion)
Phase 1 proposed DEFAULT_REQUIRED_HOURS = 8.0. However, this value does NOT exist anywhere in the current codebase. Every single usage is 7.33. Changing the default to 8.0 would alter balance calculations for ALL employees without policy — a breaking change with no business justification.
Option B: Use 7.33 (7:20) — preserve current behavior
The current hard-coded value is 7:20. Using this as the default ensures zero behavioral change during migration. All existing balances remain correct. This is the safe no-policy behavior.
Option C: Fail / show warning
Treat missing policy as a configuration error. Show a warning in UI. This forces immediate policy setup but risks breaking the attendance view for all employees until policy is configured.
Decision #2: Default Required Hours
Question: What is the default daily required work hours when no attendance policy is configured?
Why it matters: This determines what happens to all existing employees during and after migration. 8.0 would change balances; 7.33 preserves current behavior.
Options: (A) 8.0, (B) 7.33 (current), (C) fail/warn.
Recommended: Option B — 7.33 (7:20). Zero behavioral change during migration. Matches all existing code.
Needs user confirmation: YES
Phase 1 discrepancy: Phase 1 suggested DEFAULT_REQUIRED_HOURS = 8.0 without repository evidence. The repo contains only 7.33. Adopting 8.0 would be a business decision, not a technical one, and would change every employee's balance calculation.

11. Historical Attendance Strategy

When an employee's attendance policy changes (e.g., required hours change from 7:20 to 8:00), how should past attendance be treated?

Option A: Current-only (no history)

Approach: Always apply the CURRENT policy to all attendance calculations, including past months.
Pros: Simplest implementation; no date-scoping logic needed.
Cons: Historically calculated balances change retroactively; past reports show different numbers after policy change; audit trail is lost.

Option B: Effective-date resolution (like EmployeeRegion)

Approach: Store policy changes with effective dates. When calculating attendance for a given date, resolve the policy that was active on that date.
Pros: Correct historical calculation; audit trail; retroactive policy changes work correctly.
Cons: More complex resolution logic; requires Policy.effective_from_year/to_year to be properly maintained.

Option C: Store resolved values per-attendance-day

Approach: When attendance is recorded, resolve and store the applicable policy values alongside the attendance record.
Pros: Fast reads; immutable audit trail.
Cons: Schema change to Attendance table; data duplication; policy changes don't retroactively fix stored values.
Decision #3: Historical Attendance
Question: How should past attendance be calculated when the policy changes?
Why it matters: This affects report accuracy, audit compliance, and implementation complexity.
Options: (A) Current-only, (B) Effective-date resolution, (C) Store resolved values.
Recommended: Option B — Effective-date resolution. The existing Policy.effective_from_year/effective_to_year already supports this. Follow the EmployeeRegion pattern.
Needs user confirmation: YES

12. Late Analysis

Current State

Zero late-tracking logic exists. The system records when an employee punches in/out but never compares against a scheduled time. No "late" status, no late count, no late penalty.

What's Needed

  1. Scheduled start time: Must be stored per-department or per-employee (see Section 9: scheduled_start_time parameter)
  2. First-entry comparison: Compare the employee's first punch-in of the day against the scheduled start time + grace period
  3. Late computation: late_minutes = max(0, first_punch_in - scheduled_start - grace_minutes)
  4. Status display: Show 'late' status in the daily attendance view

Night Shift Complication

The system has implicit enter/exit for night shifts (00:00:00 entry, 23:59:59 exit). Late calculation for night shifts would need different scheduled times. This adds complexity.

Decision #4: Late Tracking Scope
Question: Should late tracking apply to all employees or only specific groups?
Why it matters: Not all contract types may have strict arrival requirements (e.g., doctors, on-call staff).
Options: (A) All employees, (B) Per-department enable/disable via policy, (C) Per-employee opt-in.
Recommended: Option B — Per-department via late_enabled policy parameter. Default OFF.
Needs user confirmation: YES

13. Early Leave Analysis

Current State

Zero early-leave logic exists. Same as late — no comparison against scheduled end time.

What's Needed

  1. Scheduled end time: Must be stored per-department or per-employee (Section 9: scheduled_end_time)
  2. Last-exit comparison: Compare the employee's last punch-out against the scheduled end time minus grace period
  3. Early leave computation: early_minutes = max(0, scheduled_end - grace_minutes - last_punch_out)
  4. Status display: Show 'early leave' in the daily view

Interaction with Work Hours

An employee who leaves early but already worked required_work_hours (e.g., arrived at 06:00, finished at 13:20, required = 7:20) should NOT be penalized. Early leave should only trigger when the employee hasn't completed their required hours AND left before the scheduled end.

Decision #5: Early Leave Scope
Question: Should early leave tracking mirror the late tracking configuration?
Why it matters: Same flexibility concern as late tracking.
Options: (A) Mirror late settings, (B) Independent early_leave_enabled per department.
Recommended: Option B — Independent. Some departments may want late tracking but not early leave, or vice versa.
Needs user confirmation: YES

14. Grace Period Semantics

Double-Counting Risk

If grace period is applied to both late and early leave, an employee arriving 10 minutes late and leaving 10 minutes early (with a 10-minute grace) would show as: 0 late, 0 early — but they worked 20 fewer minutes. Is this the desired behavior?

Options

Option A: Independent grace periods
Late grace and early leave grace are independent. An employee arriving 10 min late with 10-min grace = not late. Leaving 10 min early with 10-min grace = not early. The missing 20 minutes are reflected in the WORK HOURS balance, not in late/early counts.
This is the standard approach.
Option B: Combined grace budget
A single daily grace budget (e.g., 10 minutes) shared between late and early. If you use 5 minutes of grace for lateness, you have 5 left for early departure.
More complex, unusual, but prevents gaming.
Decision #6: Grace Period Semantics
Question: How should late and early-leave grace periods interact?
Why it matters: Affects employee fairness and potential gaming behavior.
Options: (A) Independent, (B) Combined budget.
Recommended: Option A — Independent. Simpler, standard, and the work-hours balance already captures the total time shortfall.
Needs user confirmation: YES

15. Balance Interaction

Current Balance Formula

monthly_balance = actual_work_hours - (duty_days × required_hours)

How Late/Early Should Interact

Late/early are informational labels on top of the existing balance calculation. They do NOT change the balance formula:

  • Balance: Still computed from actual hours vs. required hours. An employee who is 30 min late but works through lunch has the same balance as one who arrived on time and left on time.
  • Late count: A separate metric. Useful for HR reporting and policy compliance.
  • Early leave count: Same — informational.
  • Grace period: Only affects whether a punch is labeled "late" or "early"; does NOT add time to the balance.
The existing balance formula is correct. Late/early are overlay metrics, not balance modifiers.

Key Design Decisions

  1. Policy scope: Employee.department (hybrid with per-employee override)
  2. Default required hours: 7.33 (7:20) — zero behavioral change
  3. No new tables: Use existing Policy/PolicyValue infrastructure
  4. Shared service: Single resolve_attendance_policy() used by user view, manager view, and reports
  5. Late/early are overlay metrics: Do not change balance formula
  6. Grace periods are independent: Late grace ≠ early leave grace
  7. Historical resolution: Use Policy.effective_from_year/to_year (follow EmployeeRegion pattern)

22.3 Late/Early Computation

def compute_late_minutes(first_punch_in: time, scheduled_start: time, grace: int) -> int:
    """Returns late minutes, or 0 if within grace."""
    scheduled_dt = datetime.combine(date.today(), scheduled_start) + timedelta(minutes=grace)
    actual_dt = datetime.combine(date.today(), first_punch_in)
    diff = (actual_dt - scheduled_dt).total_seconds() / 60
    return max(0, int(diff))

def compute_early_leave_minutes(last_punch_out: time, scheduled_end: time, grace: int) -> int:
    """Returns early-leave minutes, or 0 if within grace."""
    scheduled_dt = datetime.combine(date.today(), scheduled_end) - timedelta(minutes=grace)
    actual_dt = datetime.combine(date.today(), last_punch_out)
    diff = (scheduled_dt - actual_dt).total_seconds() / 60
    return max(0, int(diff))

23. Open Business Decisions

Decision #1: Policy Scope
Question: What determines an employee's attendance policy?
Why it matters: Foundational design decision affecting every downstream component.
Options: (A) Contract type, (B) Department, (C) Explicit assignment, (D) Hybrid dept+override.
Recommended: D — Hybrid (department as default, per-employee override via PolicyValue).
Needs user confirmation: YES
Decision #2: Default Required Hours
Question: What is the default daily required work hours when no policy is configured?
Why it matters: 8.0 would change balances for all existing employees; 7.33 preserves current behavior.
Options: (A) 8.0, (B) 7.33 (current), (C) fail/warn.
Recommended: B — 7.33. Zero behavioral change. Matches all existing code.
Needs user confirmation: YES
Decision #3: Historical Attendance
Question: How should past attendance be calculated when policy changes?
Why it matters: Affects report accuracy and audit compliance.
Options: (A) Current-only, (B) Effective-date resolution, (C) Store resolved values.
Recommended: B — Effective-date resolution using Policy.effective_from/to_year.
Needs user confirmation: YES
Decision #4: Late Tracking Scope
Question: Should late tracking apply to all employees or specific groups?
Why it matters: Not all contract types may have strict arrival requirements.
Options: (A) All, (B) Per-department enable/disable, (C) Per-employee opt-in.
Recommended: B — Per-department via late_enabled policy parameter. Default OFF.
Needs user confirmation: YES
Decision #5: Early Leave Scope
Question: Should early leave tracking mirror late tracking?
Why it matters: Flexibility for different department policies.
Options: (A) Mirror late, (B) Independent early_leave_enabled.
Recommended: B — Independent enable/disable per department.
Needs user confirmation: YES
Decision #6: Grace Period Semantics
Question: How should late and early-leave grace periods interact?
Why it matters: Affects fairness and gaming behavior.
Options: (A) Independent, (B) Combined budget.
Recommended: A — Independent. Standard approach. Work-hours balance captures total shortfall.
Needs user confirmation: YES
Decision #7: Report Late/Early Inclusion
Question: Should late/early data appear in all reports or specific ones?
Why it matters: Affects report complexity and data volume.
Options: (A) All reports, (B) Only detailed monthly, (C) New dedicated report.
Recommended: B — Start with detailed monthly only. Expand based on feedback.
Needs user confirmation: YES

27. Final Verdict

Answering the 16 Acceptance Criteria Questions

  1. Where does an employee's duty come from?: duty_days × DAILY_DUTY_HOURS, where duty = work_days - leave - rest. Hard-coded at 7:20. Policy not yet used.
  2. How is "contractual" determined?: Employee.department stores a group code ('1'-'5'). The real contract type is Contract.contract_type_code. They are conflated in reports but not the same field.
  3. Is Contract Type the best policy scope?: No. Employee.department with per-employee override is recommended (Decision #1).
  4. How is policy assigned to employee?: Via PolicyValue with _dept_{N} suffix (dept default) or _user_{id} suffix (per-employee override).
  5. What happens if no policy?: System defaults: 7.33h, 07:00-14:20, late/early disabled (Decision #2).
  6. Where exactly is 7:20 used?: 11+ locations across attendance.py (3), admin.py (5), detailed_monthly_report_v2.py (1), analytical_report.py (1). See Section 6 table.
  7. What happens to past attendance?: Effective-date resolution (Decision #3). Policy.effective_from/to_year determines which policy applies.
  8. How is Late computed?: max(0, first_punch_in - scheduled_start - grace). Currently non-existent. New feature.
  9. How is Early Leave computed?: max(0, scheduled_end - grace - last_punch_out). Currently non-existent. New feature.
  10. What does Grace Period mean?: Minutes of tolerance before late/early is flagged. Independent for late and early (Decision #6).
  11. How do Late/Early interact with Balance?: They don't. They are informational overlay metrics. Balance = actual hours - required hours (Section 15).
  12. How do User/Manager share business logic?: Via shared resolve_attendance_policy() in core/attendance_policy.py. Current duplication (attendance.py + admin.py) is extracted.
  13. How do Reports consume the new policy?: Replace hard-coded DAILY_REQUIRED_HOURS with per-employee policy lookup (Section 18).
  14. What is the exact General Policies UI?: New /admin/policies/attendance page with a table: Department | Required Hours | Start/End Time | Late/Early toggles + grace. Follow policy_leave.html pattern (Section 19).
  15. What migration/data changes?: None. No new tables. Only new PolicyValue rows (category='attendance') seeded via the admin UI.
  16. What tests?: Unit tests for resolve_attendance_policy, compute_late_minutes, compute_early_leave_minutes. Integration tests for admin UI save, user view balance, report generation (Section 25).
