Employee Override

آیا Employee Override لازم است؟

Option A: بدون Override
Policy فقط بر اساس Employment Type است. همه کارمندان یک نوع عضویت سیاست یکسان دارند.
Pros: ساده، یکپارچه
Cons: انعطاف‌پذیری کم — اگر یک قراردادی ساعت ورود متفاوت داشته باشد، امکان تنظیم نیست.
Option B: Per-Employee Override (پیشنهادی)
سیاست پیش‌فرض از Employment Type می‌آید، اما می‌توان برای یک employee خاص override کرد.
Pros: انعطاف‌پذیر، استثناها قابل مدیریت
Cons: پیچیدگی بیشتر در Resolution
Pattern: مشابه _user_{user_id} در Phase 2.
Decision #1: Employee Override

Question: آیا باید Per-Employee Override برای Attendance Policy وجود داشته باشد؟

Why it matters: برخی کارمندان ممکن است شرایط خاص داشته باشند (مثلاً ساعت کاری متفاوت).

Recommended: Option B — بله، از همان الگوی PolicyValue با _user_{id} suffix استفاده شود.

3. Policy Resolution Flow

الگوریتم Resolution

def resolve_attendance_policy(employee: Employee, target_date: date) -> AttendancePolicy:
    """
    Resolve attendance policy for an employee on a specific date.
    Priority: Employee Override > Employment Type Default > System Default
    """
    employment_type = employee.department  # '1'-'5' or None

    # 1. Employee Override (highest priority)
    if employment_type:
        override = get_policy_value(
            category='attendance',
            key_suffix=f'_user_{employee.user_id}'
        )
        if override:
            return build_policy_from_values(override)

    # 2. Employment Type Default
    if employment_type in ('1', '2', '3', '4', '5'):
        type_policy = get_policy_values(
            category='attendance',
            key_pattern=f'_dept_{employment_type}'
        )
        if type_policy:
            return build_policy_from_values(type_policy)

    # 3. System Default (fallback)
    return get_system_default_policy()

4. Required Work Design

سوال کلیدی: آیا Required Work مستقل از Start/End است؟

در سیستم متعارف:

  • Scheduled Span = End - Start (مثلاً 07:00 تا 14:00 = 7 ساعت)
  • Required Work = ساعات موظفی واقعی (ممکن است با Break متفاوت باشد)

مثال: کارمند از 07:00 تا 14:00 حضور دارد (7 ساعت)، اما با 20 دقیقه Break، موظفی 6 ساعت و 40 دقیقه است.

Repository Evidence: هیچ مفهوم Break در کد وجود ندارد. تمام محاسبات DAILY_DUTY_HOURS = 7.33 را به‌عنوان یک ثابت استفاده می‌کنند. به نظر می‌رسد Scheduled Span = Required Work فرض شده است.
Decision #2: Required Work vs Scheduled Span

Question: آیا required_work_hours مستقل از scheduled_end - scheduled_start باشد؟

Why it matters: اگر Break وجود داشته باشد، تفاوت ایجاد می‌شود. فعلاً Break پیاده‌سازی نمی‌شود.

Options:

(A) Required Work = Scheduled Span (ساده، بدون Break)

(B) Required Work مستقل ذخیره شود (آینده‌پذیر برای Break)

Recommended: Option A — فعلاً بدون Break. اگر در آینده Break اضافه شد، required_work = span - break محاسبه شود.

Needs confirmation: YES

6. Late Policy Design

تعریف Late

Late = Actual Check-in > Scheduled Start + Grace Period

Mapping ساعت مرجع:
  • Late به ساعت ورود / Scheduled Start نیاز دارد
  • مقایسه: first_punch_in vs scheduled_start + grace_minutes

پارامترهای Late Policy

پارامترTypeتوضیح
late_enabledbooleanآیا Late Tracking فعال است؟
late_allowed_minutesintegerGrace Period (دقیقه)
late_reference_modeenumFIXED_TIME | SHIFT

Reference Mode

FIXED_TIME (فعلی)
  • ساعت مرجع از AttendancePolicyDay.start_time خوانده می‌شود
  • برای هر روز هفته می‌تواند متفاوت باشد
SHIFT (آینده)
  • ساعت مرجع از Shift Assignment کارمند خوانده می‌شود
  • فعلاً پیاده‌سازی نمی‌شود
  • معماری باید آماده پذیرش باشد

محاسبه Late

def compute_late_minutes(
    first_punch_in: time,
    policy_day: AttendancePolicyDay,
    late_policy: LatePolicy
) -> int:
    """
    Returns late minutes, or 0 if within grace or disabled.
    """
    if not late_policy.enabled:
        return 0

    if late_policy.reference_mode == 'FIXED_TIME':
        scheduled_start = policy_day.start_time
    elif late_policy.reference_mode == 'SHIFT':
        scheduled_start = resolve_shift_start(...)  # Future
    else:
        return 0

    scheduled_dt = datetime.combine(date.today(), scheduled_start)
    scheduled_dt += timedelta(minutes=late_policy.allowed_minutes)  # Grace

    actual_dt = datetime.combine(date.today(), first_punch_in)
    diff_minutes = (actual_dt - scheduled_dt).total_seconds() / 60

    return max(0, int(diff_minutes))

7. Early Leave Policy Design

تعریف Early Leave

Early Leave = Scheduled End - Grace Period > Actual Check-out

Mapping ساعت مرجع:
  • Early Leave به ساعت خروج / Scheduled End نیاز دارد
  • مقایسه: scheduled_end - grace_minutes vs last_punch_out

استقلال از Late

Late و Early Leave باید کاملاً مستقل باشند. فعال بودن یکی دیگری را فعال نمی‌کند.

محاسبه Early Leave

def compute_early_leave_minutes(
    last_punch_out: time,
    policy_day: AttendancePolicyDay,
    early_leave_policy: EarlyLeavePolicy
) -> int:
    """
    Returns early leave minutes, or 0 if within grace or disabled.
    """
    if not early_leave_policy.enabled:
        return 0

    if early_leave_policy.reference_mode == 'FIXED_TIME':
        scheduled_end = policy_day.end_time
    elif early_leave_policy.reference_mode == 'SHIFT':
        scheduled_end = resolve_shift_end(...)  # Future
    else:
        return 0

    scheduled_dt = datetime.combine(date.today(), scheduled_end)
    scheduled_dt -= timedelta(minutes=early_leave_policy.allowed_minutes)  # Grace

    actual_dt = datetime.combine(date.today(), last_punch_out)
    diff_minutes = (scheduled_dt - actual_dt).total_seconds() / 60

    return max(0, int(diff_minutes))

8. Grace Period Semantics

سوال: آیا Grace Periodهای Late و Early Leave مشترک هستند؟

مثال: Grace = 15 دقیقه

  • کارمند 10 دقیقه دیر می‌آید → در Grace است → Late = 0
  • همان کارمند 10 دقیقه زود می‌رود → در Grace است → Early = 0
  • اما مجموعاً 20 دقیقه کم کار کرده
Option A: Grace Periodهای مستقل (پیشنهادی)
  • Late Grace و Early Leave Grace مستقل هستند
  • یک نفر می‌تواند Late = 0 و Early = 0 باشد اما Balance منفی
  • Balance از Work Hours محاسبه می‌شود — Grace فقط برچسب Late/Early را کنترل می‌کند
اینگونه Double Counting رخ نمی‌دهد.
Option B: Combined Grace Budget
  • یک Grace Pool روزانه (مثلاً 15 دقیقه)
  • اگر 10 دقیقه برای Late استفاده شود، 5 دقیقه برای Early باقی می‌ماند
پیچیدگی بالا — برای فاز اول توصیه نمی‌شود.
نتیجه: Grace Period فقط برچسب "Late" / "Early Leave" را تعیین می‌کند. Balance مستقل از این برچسب‌ها از Work Hours واقعی محاسبه می‌شود. بنابراین Double Counting رخ نمی‌دهد.

9. Fixed Time vs Shift Reference

Abstraction Layer

برای آینده‌پذیر کردن Shift، یک Abstraction معرفی می‌کنیم:

class ReferenceTimeResolver(ABC):
    @abstractmethod
    def get_scheduled_start(self, employee: Employee, date: date) -> time:
        pass

    @abstractmethod
    def get_scheduled_end(self, employee: Employee, date: date) -> time:
        pass


class FixedTimeResolver(ReferenceTimeResolver):
    """Reads from AttendancePolicyDay"""
    def get_scheduled_start(self, employee, date):
        policy = resolve_attendance_policy(employee, date)
        weekday = to_jalali_weekday(date.weekday())
        day = policy.get_day(weekday)
        return day.start_time if day.is_working_day else None

    def get_scheduled_end(self, employee, date):
        policy = resolve_attendance_policy(employee, date)
        weekday = to_jalali_weekday(date.weekday())
        day = policy.get_day(weekday)
        return day.end_time if day.is_working_day else None


class ShiftResolver(ReferenceTimeResolver):
    """Future: reads from Shift Assignment"""
    def get_scheduled_start(self, employee, date):
        shift = resolve_employee_shift(employee, date)
        return shift.start_time if shift else None

    def get_scheduled_end(self, employee, date):
        shift = resolve_employee_shift(employee, date)
        return shift.end_time if shift else None


def get_reference_resolver(mode: str) -> ReferenceTimeResolver:
    if mode == 'FIXED_TIME':
        return FixedTimeResolver()
    elif mode == 'SHIFT':
        return ShiftResolver()
    else:
        raise ValueError(f"Unknown reference mode: {mode}")

مزیت

با این Abstraction، تغییر از FIXED_TIME به SHIFT در آینده نیازمند تغییر در Business Logic نیست — فقط Reference Resolver عوض می‌شود.

11. Historical Policy Strategy

مسئله

وقتی Policy تغییر می‌کند، Attendance گذشته نباید بازنویسی شود.

مثال
  • Sep 1: Policy = 07:00 → 14:00
  • Sep 10: Policy changes to 07:00 → 13:30
  • Sep 1 attendance باید با Policy قدیمی (14:00) محاسبه شود

راه‌حل: Effective Date Resolution

ColumnTypeتوضیح
effective_from_yearintegerسال شمسی شروع اعتبار
effective_to_yearinteger (nullable)سال شمسی پایان اعتبار (null = جاری)
def resolve_attendance_policy(employee: Employee, target_date: date) -> AttendancePolicy:
    target_year_j = jdatetime.date.fromgregorian(date=target_date).year

    policies = db.query(AttendancePolicy).filter(
        AttendancePolicy.employment_type_code == employee.department,
        AttendancePolicy.effective_from_year <= target_year_j,
        or_(
            AttendancePolicy.effective_to_year == None,
            AttendancePolicy.effective_to_year >= target_year_j
        ),
        AttendancePolicy.is_active == True
    ).all()

    if policies:
        # Return the most specific (latest effective_from)
        return max(policies, key=lambda p: p.effective_from_year)

    return get_system_default_policy()

مزیت

این الگو با EmployeeRegion.effective_from/effective_to و Contract.start_date/end_date سازگار است و همان رفتار temporal resolution را ارائه می‌دهد.

12. Balance Calculation Model

رابطه متغیرها

Required Work Hours (from Policy) │ ├── per-day: scheduled_end - scheduled_start (or explicit) └── per-month: duty_days × required_work_hours Actual Work Hours (from Attendance) │ └── sum of work_hours per day Balance = Actual Work Hours - Required Work Hours Late/Early (INFORMATIONAL) │ ├── late_minutes: first_punch_in vs scheduled_start + grace └── early_leave_minutes: scheduled_end - grace vs last_punch_out ⚠️ Late/Early do NOT affect Balance directly. ⚠️ They are labels for HR reporting.

نکته کلیدی: Double Counting Prevention

Late/Early برچسب‌های اطلاعاتی هستند و تأثیری بر Balance ندارند.

مثال:

  • کارمند موظفی: 07:00 → 14:00 (7 ساعت)
  • ورود: 07:15 (15 دقیقه دیر، Grace = 10 → Late = 5 دقیقه)
  • خروج: 14:00 (سر وقت)
  • کارکرد واقعی: 6 ساعت و 45 دقیقه
  • Balance: 6:45 - 7:00 = -15 دقیقه
  • Late: 5 دقیقه (برچسب)

Late فقط گزارش می‌شود، اما Balance از کارکرد واقعی محاسبه شده. Double Counting وجود ندارد.

Open Business Decisions Summary

Decision #1: Employee Override

Question: Should per-employee override be supported?

Recommended: Yes — use _user_{id} suffix pattern.

Needs confirmation: YES

Decision #2: Required Work vs Scheduled Span

Question: Should required_work_hours be independent from (end - start)?

Recommended: No — assume equality for now. Add Break in future if needed.

Needs confirmation: YES

Decision #3: Weekly Schedule Storage

Question: Which database model for weekly schedule?

Recommended: Option B — Child table AttendancePolicyDay.

Needs confirmation: YES

Decision #4: Meaning of Scheduled Times

Question: Do scheduled times include break?

Why it matters: If 07:00-14:00 includes a break, required work < 7 hours.

Repository Evidence: No break concept found. All calculations use 7:20 directly.

Recommended: Assume scheduled span = required work (no break) until business clarifies.

Needs confirmation: YES

Decision #5: Behavior on Missing Policy

Question: What if an employee has no department or policy not found?

Recommended: Use system default (7:20, 07:00-14:20, late/early disabled). Show warning in admin.

Needs confirmation: YES

Decision #6: Late/Early on Non-Working Days

Question: Should late/early be computed if employee works on a non-working day (e.g., Friday)?

Recommended: No — if is_working_day=false, no late/early labels. Work hours still count toward balance.

Needs confirmation: YES
